Context & my role

A new platform with enterprise customers waiting

KT Impact was building a platform for commercial electric fleets: given a freight lane, find where and when trucks can charge. The product only works if three external data domains (vehicle telematics, routing, and charging networks) arrive on time and in a shape the platform can trust.

Enterprise fleet customers were lined up before the platform was production-ready, so delivery and customer implementation had to run in parallel instead of in sequence.

I owned
Delivery plan and roadmap sequencing, program budget, vendor selection, release cadence, and the enterprise implementation path.
I influenced
Integration architecture and data schemas (defined with Engineering), product scope trade-offs, and SLA thresholds.
Partners
Product, Engineering, Data, Operations, external telematics and charging-network providers, and customer fleet teams.
Problem & constraints

Integration risk and customer pressure at the same time

Each data provider had its own formats, update frequency, and failure modes. Without agreed contracts, every new fleet customer turned into a custom integration, and production issues landed on whichever engineer was closest.

No written API contracts or schemas for the three external feeds
Enterprise go-lives scheduled before the platform was production-stable
Production downtime around 8.5%, with no shared way to rank issues
Small team and a fixed budget: every vendor and scope decision had a cost
Key decisions

Two calls that shaped the program

Define integration contracts before taking more customers live

Options
(a) Keep taking customers live and build integrations case by case · (b) Pause new go-lives to write API contracts and data schemas for each feed first
Chose
Contracts first, with go-lives sequenced right behind them
Tradeoff
It cost a few weeks up front, and some customer conversations had to be reset. In return, every later account used the same integration path instead of a custom build. That reuse is the main reason time-to-launch dropped 35%.

Rank engineering issues by customer impact instead of by who escalated loudest

Options
(a) Let each team triage its own issues · (b) Hold one weekly cross-team triage, ranked by customer impact
Chose
One weekly triage, ranked by customer impact
Tradeoff
Some internal and tech-debt items waited longer. In return, the issues causing the most customer-facing downtime were fixed first, and blockers that crossed team lines had a single forum to get resolved.
Execution

How the delivery ran

Four mechanisms connected the platform build to customer go-lives.

Integration contracts
Wrote the API contracts, data schemas, and integration requirements for the telematics, routing, and charging-network feeds with Engineering. Each new enterprise account then followed a known path.
Release cadence & scope controls
Set a fixed release cadence with capacity planning and scope controls, so customer commitments matched what Engineering could actually ship.
SLA thresholds
Defined SLA thresholds for production readiness. These set the bar a release had to meet before an enterprise account was moved onto it.
Weekly impact-ranked triage
A cross-team triage each week, with issues ranked by customer impact. Blockers that crossed team lines had an owner and a date before the meeting ended.

Retrospective

What I'd do differently

Set an SLO target at the start, not only thresholds. Downtime improved from 8.5% to 6.6%, which is real progress but still too high for an enterprise product. A stated reliability target and an error budget from the beginning would have made the case for reliability work earlier and with more force.

Put customer-side integration testing in the contract. Several go-live delays came from differences in how each customer's own systems behaved. A required test stage on the customer's side would have caught those before go-live.
